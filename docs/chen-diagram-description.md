# Диаграмма "Сущность-Связь" в нотации Питера Чена
## Система управления заявками Helpdesk

---

## Обозначения нотации Питера Чена:

- **Прямоугольник** — Сущность (Entity)
- **Овал** — Атрибут (Attribute)
- **Овал с подчеркнутым текстом** — Ключевой атрибут (Primary Key)
- **Ромб** — Связь (Relationship)
- **Линии** — Соединения между элементами
- **Кардинальность**: 1:1, 1:N, M:N

---

## Описание связей (ромбы):

### Связь 1: Пользователь ←→ Роль
**Ромб**: "имеет роль"
- **Кардинальность**: N:1 (много пользователей к одной роли)
- **Описание**: Каждый пользователь имеет одну роль, роль может быть у многих пользователей
- **Участие**: обязательное для Пользователя (1, 1)

```
Пользователь ----N---- [имеет роль] ----1---- Роль
```

### Связь 2: Заявка ←→ Пользователь (автор)
**Ромб**: "создана пользователем"
- **Кардинальность**: N:1 (много заявок к одному пользователю)
- **Описание**: Каждую заявку создает один пользователь, пользователь может создать много заявок
- **Участие**: обязательное для Заявки (1, 1)

```
Заявка ----N---- [создана пользователем] ----1---- Пользователь
```

### Связь 3: Заявка ←→ Пользователь (исполнитель)
**Ромб**: "назначена на"
- **Кардинальность**: N:1 (много заявок к одному оператору)
- **Описание**: Заявка может быть назначена на одного оператора, оператор может иметь много заявок
- **Участие**: необязательное для Заявки (0, 1)

```
Заявка ----N---- [назначена на] ----1---- Пользователь
                                          (оператора)
```

### Связь 4: Заявка ←→ Категория
**Ромб**: "имеет категорию"
- **Кардинальность**: N:1 (много заявок к одной категории)
- **Описание**: Каждая заявка имеет одну категорию, категория может быть у многих заявок
- **Участие**: обязательное для Заявки (1, 1)

```
Заявка ----N---- [имеет категорию] ----1---- Категория
```

### Связь 5: Заявка ←→ Приоритет
**Ромб**: "имеет приоритет"
- **Кардинальность**: N:1 (много заявок к одному приоритету)
- **Описание**: Каждая заявка имеет один приоритет, приоритет может быть у многих заявок
- **Участие**: обязательное для Заявки (1, 1)

```
Заявка ----N---- [имеет приоритет] ----1---- Приоритет
```

### Связь 6: Заявка ←→ Статус
**Ромб**: "находится в статусе"
- **Кардинальность**: N:1 (много заявок к одному статусу)
- **Описание**: Каждая заявка имеет один статус, статус может быть у многих заявок
- **Участие**: обязательное для Заявки (1, 1)

```
Заявка ----N---- [находится в статусе] ----1---- Статус
```

### Связь 7: Комментарий ←→ Заявка
**Ромб**: "принадлежит заявке"
- **Кардинальность**: N:1 (много комментариев к одной заявке)
- **Описание**: Каждый комментарий принадлежит одной заявке, заявка может иметь много комментариев
- **Участие**: обязательное для Комментария (1, 1), необязательное для Заявки (0, N)

```
Комментарий ----N---- [принадлежит заявке] ----1---- Заявка
```

### Связь 8: Комментарий ←→ Пользователь
**Ромб**: "написан пользователем"
- **Кардинальность**: N:1 (много комментариев к одному пользователю)
- **Описание**: Каждый комментарий написан одним пользователем, пользователь может написать много комментариев
- **Участие**: обязательное для Комментария (1, 1)

```
Комментарий ----N---- [написан пользователем] ----1---- Пользователь
```

### Связь 9: История ←→ Заявка
**Ромб**: "относится к заявке"
- **Кардинальность**: N:1 (много записей истории к одной заявке)
- **Описание**: Каждая запись истории относится к одной заявке, заявка может иметь много записей истории
- **Участие**: обязательное для Истории (1, 1), необязательное для Заявки (0, N)

```
История ----N---- [относится к заявке] ----1---- Заявка
```

### Связь 10: История ←→ Пользователь
**Ромб**: "изменена пользователем"
- **Кардинальность**: N:1 (много записей истории к одному пользователю)
- **Описание**: Каждое изменение вносится одним пользователем, пользователь может внести много изменений
- **Участие**: обязательное для Истории (1, 1)

```
История ----N---- [изменена пользователем] ----1---- Пользователь
```

## Дополнительные пояснения:

1. **Составные связи**:
   - Заявка связана с Пользователем дважды: один раз как "создатель" (created_by), второй раз как "исполнитель" (assigned_to)
   - Это разные роли в контексте заявки

2. **Кардинальность**:
   - **1:1** — один к одному
   - **1:N** — один ко многим
   - **M:N** — многие ко многим (в данной модели не используется)

3. **Участие (Participation)**:
   - **(1, 1)** — обязательное участие (каждая сущность должна участвовать в связи)
   - **(0, 1)** — необязательное участие (сущность может не участвовать в связи)
   - **(0, N)** — необязательное участие, множественное
   - **(1, N)** — обязательное участие, множественное

4. **Ключевые атрибуты**:
   - Все первичные ключи подчеркнуты (в диаграмме отображаются подчеркнутым текстом)
   - Внешние ключи не отображаются как отдельные атрибуты, а представлены связями

## Инструкция по построению визуальной диаграммы:

### Для построения диаграммы вручную:

1. **Нарисуйте все сущности** (8 прямоугольников):
   - Пользователь, Роль, Заявка, Категория, Приоритет, Статус, Комментарий, История

2. **Для каждой сущности нарисуйте атрибуты** (овалы):
   - Соедините овалы с прямоугольниками линиями
   - Подчеркните первичные ключи

3. **Нарисуйте связи** (10 ромбов):
   - Разместите ромбы между связанными сущностями
   - Подпишите название связи внутри ромба

4. **Укажите кардинальность**:
   - Около линий укажите "1" или "N" (или "M")
   - Можно также указать (0,1) или (1,N) для детализации

5. **Расположение элементов**:
   - Центральной сущностью является **Заявка**
   - Вокруг нее расположите связанные справочники: Категория, Приоритет, Статус
   - Пользователь и Роль — в верхней части
   - Комментарий и История — в нижней части

### Рекомендуемые инструменты для визуализации:

- **Draw.io (diagrams.net)** — бесплатный онлайн-редактор
- **Lucidchart** — профессиональный инструмент для диаграмм
- **Microsoft Visio** — для Windows
- **yEd Graph Editor** — бесплатный редактор графов
- **Creately** — онлайн-инструмент
- **ERDPlus** — специализированный инструмент для ER-диаграмм

## Ключевые особенности модели данных Helpdesk:

1. **Централизованная сущность**: Заявка (Ticket) является центральной, с ней связаны все остальные сущности
2. **Аудит изменений**: Сущность История обеспечивает полный аудит всех изменений заявок
3. **Гибкая система прав**: Роли пользователей определяют доступные операции
4. **Справочники**: Категория, Приоритет, Статус — изменяемые справочники
5. **Коммуникация**: Комментарии обеспечивают взаимодействие между пользователями и операторами
