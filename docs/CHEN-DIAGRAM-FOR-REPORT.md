# ДИАГРАММА "СУЩНОСТЬ-СВЯЗЬ" В НОТАЦИИ ПИТЕРА ЧЕНА
## Для включения в отчет о системе Helpdesk

---

## КРАТКОЕ ОПИСАНИЕ

Диаграмма в нотации Питера Чена представляет концептуальную модель данных системы управления заявками Helpdesk. Диаграмма показывает все сущности предметной области, их атрибуты и связи между ними.

---

## ОБОЗНАЧЕНИЯ НОТАЦИИ

| Элемент | Графическое обозначение | Описание |
|---------|-------------------------|----------|
| **Сущность** | Прямоугольник | Объект предметной области (User, Ticket и т.д.) |
| **Атрибут** | Овал | Свойство сущности (login, email и т.д.) |
| **Ключевой атрибут** | Овал с подчеркиванием | Первичный ключ сущности (user_id, ticket_id) |
| **Связь** | Ромб | Отношение между сущностями (имеет, создана и т.д.) |
| **Линия** | Прямая линия | Соединяет элементы диаграммы |

### Кардинальность связей:

- **1:1** — Один к одному (каждый элемент связан ровно с одним)
- **1:N** — Один ко многим (один элемент связан со многими)
- **M:N** — Многие ко многим (не используется в данном проекте)

### Обозначение участия в связи:

- **(1, 1)** — Обязательное участие (каждая сущность должна участвовать)
- **(0, 1)** — Необязательное участие (сущность может не участвовать)
- **(0, N)** — Необязательное участие множества
- **(1, N)** — Обязательное участие хотя бы одного

## СУЩНОСТИ СИСТЕМЫ

### 1. ПОЛЬЗОВАТЕЛЬ (User)
**Ключевой атрибут**: user_id (BIGINT)

**Атрибуты**:
- login (VARCHAR(50), UNIQUE) — Логин для входа
- password_hash (VARCHAR(255)) — BCrypt хеш пароля
- full_name (VARCHAR(100)) — Полное имя
- email (VARCHAR(100), UNIQUE) — Email адрес

**Роль**: Может быть создателем заявок, исполнителем (оператором), автором комментариев

---

### 2. РОЛЬ (Role)
**Ключевой атрибут**: role_id (BIGINT)

**Атрибуты**:
- name (VARCHAR(50), UNIQUE) — Название роли

**Значения**: USER, OPERATOR, ADMIN

**Роль**: Определяет права доступа пользователя

---

### 3. ЗАЯВКА (Ticket) — ЦЕНТРАЛЬНАЯ СУЩНОСТЬ
**Ключевой атрибут**: ticket_id (BIGINT)

**Атрибуты**:
- ticket_number (VARCHAR(20), UNIQUE) — Уникальный номер (TKT-YYYY-NNNN)
- title (VARCHAR(200)) — Заголовок заявки
- description (TEXT) — Подробное описание проблемы
- created_at (TIMESTAMP) — Дата и время создания
- updated_at (TIMESTAMP) — Дата и время последнего обновления

**Роль**: Основной объект системы, содержит информацию о запросе пользователя

---

### 4. КАТЕГОРИЯ (Category)
**Ключевой атрибут**: category_id (BIGINT)

**Атрибуты**:
- name (VARCHAR(100), UNIQUE) — Название категории

**Значения**: Программное обеспечение, Оборудование, Сеть, Доступы, Прочее

**Роль**: Классификация заявок по типу проблемы

---

### 5. ПРИОРИТЕТ (Priority)
**Ключевой атрибут**: priority_id (BIGINT)

**Атрибуты**:
- name (VARCHAR(50), UNIQUE) — Название приоритета

**Значения**: Низкий, Средний, Высокий, Критический

**Роль**: Определяет срочность обработки заявки

---

### 6. СТАТУС (Status)
**Ключевой атрибут**: status_id (BIGINT)

**Атрибуты**:
- name (VARCHAR(50), UNIQUE) — Название статуса

**Значения**: Новая, В работе, Решена, Закрыта

**Роль**: Отражает текущее состояние заявки в жизненном цикле

---

### 7. КОММЕНТАРИЙ (Comment)
**Ключевой атрибут**: comment_id (BIGINT)

**Атрибуты**:
- content (TEXT) — Текст комментария
- created_at (TIMESTAMP) — Дата и время создания

**Роль**: Обеспечивает коммуникацию между пользователями и операторами

---

### 8. ИСТОРИЯ ЗАЯВКИ (TicketHistory)
**Ключевой атрибут**: history_id (BIGINT)

**Атрибуты**:
- field_name (VARCHAR(100)) — Название измененного поля
- old_value (VARCHAR(500)) — Старое значение
- new_value (VARCHAR(500)) — Новое значение
- changed_at (TIMESTAMP) — Дата и время изменения

**Роль**: Аудит всех изменений заявки для прослеживаемости

## СВЯЗИ МЕЖДУ СУЩНОСТЯМИ

### 1. Пользователь ←→ Роль
**Тип связи**: "имеет роль"
**Кардинальность**: N:1 (много пользователей к одной роли)
**Описание**: Каждый пользователь имеет одну роль. Роль может быть назначена многим пользователям.

### 2. Заявка ←→ Пользователь (создатель)
**Тип связи**: "создана пользователем"
**Кардинальность**: N:1 (много заявок от одного пользователя)
**Описание**: Каждую заявку создает один пользователь. Пользователь может создать много заявок.

### 3. Заявка ←→ Пользователь (исполнитель)
**Тип связи**: "назначена на"
**Кардинальность**: N:1 (много заявок к одному оператору)
**Описание**: Заявка может быть назначена на одного оператора (необязательно). Оператор может иметь много заявок.

### 4. Заявка ←→ Категория
**Тип связи**: "имеет категорию"
**Кардинальность**: N:1 (много заявок одной категории)
**Описание**: Каждая заявка имеет одну категорию. Категория может быть у многих заявок.

### 5. Заявка ←→ Приоритет
**Тип связи**: "имеет приоритет"
**Кардинальность**: N:1 (много заявок одного приоритета)
**Описание**: Каждая заявка имеет один приоритет. Приоритет может быть у многих заявок.

### 6. Заявка ←→ Статус
**Тип связи**: "находится в статусе"
**Кардинальность**: N:1 (много заявок в одном статусе)
**Описание**: Каждая заявка имеет один текущий статус. Статус может быть у многих заявок.

### 7. Комментарий ←→ Заявка
**Тип связи**: "принадлежит заявке"
**Кардинальность**: N:1 (много комментариев к одной заявке)
**Описание**: Каждый комментарий принадлежит одной заявке. Заявка может иметь много комментариев.

### 8. Комментарий ←→ Пользователь
**Тип связи**: "написан пользователем"
**Кардинальность**: N:1 (много комментариев от одного пользователя)
**Описание**: Каждый комментарий написан одним пользователем. Пользователь может написать много комментариев.

### 9. История ←→ Заявка
**Тип связи**: "относится к заявке"
**Кардинальность**: N:1 (много записей истории к одной заявке)
**Описание**: Каждая запись истории относится к одной заявке. Заявка может иметь много записей истории.

### 10. История ←→ Пользователь
**Тип связи**: "изменена пользователем"
**Кардинальность**: N:1 (много изменений от одного пользователя)
**Описание**: Каждое изменение вносится одним пользователем. Пользователь может внести много изменений.

## ОСОБЕННОСТИ МОДЕЛИ

### 1. Центральная роль сущности "Заявка"
Заявка является центральной сущностью, с которой связаны все остальные элементы системы. Это отражает основное назначение системы — управление заявками.

### 2. Двойная связь Заявка-Пользователь
Заявка связана с сущностью Пользователь дважды:
- **created_by** — кто создал заявку (обязательная связь)
- **assigned_to** — кому назначена заявка (необязательная связь)

Это разные роли в контексте одной заявки.

### 3. Справочные сущности
Роль, Категория, Приоритет, Статус — являются справочниками, которые редко изменяются и используются для классификации.

### 4. Аудит изменений
Сущность "История заявки" обеспечивает полный аудит всех изменений, позволяя отследить, кто, когда и что изменил в заявке.

### 5. Коммуникация
Сущность "Комментарий" обеспечивает двустороннюю коммуникацию между пользователями и операторами в рамках одной заявки.

## СООТВЕТСТВИЕ РЕАЛИЗАЦИИ

Диаграмма в нотации Питера Чена полностью соответствует:

✅ **Java-сущностям** (`/src/main/java/com/helpdesk/entity/`)
- Каждая сущность на диаграмме соответствует Java-классу с аннотацией `@Entity`
- Атрибуты соответствуют полям класса
- Связи реализованы через аннотации `@ManyToOne`, `@OneToMany`, `@JoinColumn`

✅ **Таблицам PostgreSQL** (`helpdesk_db`)
- Каждая сущность соответствует таблице в БД
- Ключевые атрибуты — это `PRIMARY KEY` с типом `BIGSERIAL`
- Связи реализованы через `FOREIGN KEY`

✅ **REST API** (`/api/...`)
- Эндпоинты построены на основе сущностей (`/api/tickets`, `/api/users` и т.д.)
- JSON-структуры соответствуют атрибутам сущностей

## ЗАКЛЮЧЕНИЕ

Диаграмма в нотации Питера Чена представляет концептуальную модель данных системы Helpdesk на высоком уровне абстракции, показывая семантику связей между сущностями предметной области.

**Преимущества данной диаграммы**:
- Наглядно показывает структуру данных системы
- Легко читается без технических знаний
- Показывает смысл связей ("создана пользователем", "имеет категорию")
- Не зависит от конкретной СУБД
- Служит основой для проектирования физической модели БД

**Область применения**:
- Документирование системы
- Обучение новых разработчиков
- Анализ требований к БД
- Согласование модели данных с заказчиком
- Основа для ER-диаграмм в других нотациях (crow's foot, UML)
